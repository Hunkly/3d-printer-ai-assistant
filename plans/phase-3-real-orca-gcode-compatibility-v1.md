Status: APPROVED

This is a plan-only correction. It does not modify production or tests, stage

## Real reproduction

The published Phase 3 chain now reaches the installed OrcaSlicer 2.3.2 with
the selected material `Bambu PLA Tough+ @base` and raw
`filament_type = ["PLA"]`. A real software-only invocation using the actual
realization and `--slice 1` returned `0` and produced the exact run-owned
`plate_1.gcode`. Increment 3 then rejected that candidate as
`slice_output_invalid` before parser-derived facts could be accepted.

The retained local real output evidence is under the existing disposable/runtime
workspaces, including a roughly 443 KB `plate_1.gcode` generated by Orca 2.3.2.
It was inspected by distinct-line extraction only; no full G-code dump is part
of this plan.

## Root cause

The owner is `_is_structurally_valid_gcode()` in
`src/print_engineer/adapters/slicer/execution.py`.

The current algorithm is:

1. Decode bytes as UTF-8 with replacement.
2. Split into lines.
3. Remove everything from the first `;` onward and strip whitespace.
4. Ignore empty results, including blank lines and comment-only lines.
5. Split each remaining line on whitespace.
6. Require the first token to match `^[GMTgmt]\d+$`.
7. Require every remaining token to match
   `^[A-Za-z][-+]?(?:\d+(?:\.\d*)?|\.\d+)(?:[eE][-+]?\d+)?$`.
8. Require at least one command line.

This incorrectly rejects decimal command IDs such as `M9833.2`, command-only
Orca forms with supported bare flags, and M1002 textual extensions. It does not
move or duplicate `parse_gcode()` fact extraction: after structural validation,
`execute()` calls `parse_gcode(candidate)`, requires a positive parsed
`layer_count`, and otherwise returns `slice_facts_invalid`.

## Proposed grammar

### Command token

Accept exactly one ASCII `G`, `M`, or `T` letter, followed by one or more
decimal digits, with at most one decimal suffix consisting of a dot and one or
more decimal digits:

```text
^[GMTgmt][0-9]+(?:\.[0-9]+)?$
```

This is syntax-based rather than a hard-coded list of every numeric command
ID. It accepts the observed `M9833.2` and other observed decimal IDs while
rejecting `G`, `G foo`, `G1.`, `G1.2.3`, signed command IDs, and arbitrary
non-G/M/T command words. It does not assign semantic meaning to the decimal
suffix and is not a G-Code interpreter.

### Standard parameters

For ordinary commands, accept the existing numeric parameter token grammar:

```text
^[A-Za-z][-+]?(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][-+]?[0-9]+)?$
```

The parameter letter is one ASCII letter and its value is a signed decimal or
scientific-notation numeric value. A command may have no parameters, as real
Orca output contains command-only lines such as `M17` and `M400`.

### Bare flags

A bare single-letter token is structurally valid only in a command-specific
allowlist justified by the inspected output. The initial allowlist is:

```text
G28: X
M1006: W
M17: D, R, S
M18: X, Y, Z
M211: R, S
M620: M
M900: C, R, S
```

The implementation must validate the full command line, not merely permit a
bare letter after every command. Therefore `G1 X` remains rejected unless new
real evidence and a separately approved correction establishes that form.
The generic `G28` bare-flag allowlist contains only `X`; `Z` must not be added
to it.

### Conditional G28 Z form

For command `G28`, separately from the generic bare-flag allowlist, accept the
exact parameterized form:

```text
G28 Z P<numeric> T<numeric>
```

`P` and `T` are both required, and the observed order `Z`, then `P`, then `T`
is required. `<numeric>` reuses the standard numeric parameter value grammar
above, so the observed forms `G28 Z P0 T140` and `G28 Z P0 T300` are valid.
This narrow rule does not admit `G28 Z`, `G28 Z P0`, or `G28 Z T140`, and it
must not be implemented as a generic `{"X", "Z"}` bare-flag check. No other
G28 Z parameter combination is admitted without separate real Orca evidence.

### Orca textual extensions

Textual payloads are accepted only for explicit command IDs and exact forms
observed in the real output:

```text
M1002 gcode_claim_action\s*:\s*[0-9]+
M1002 set_gcode_claim_speed_level\s*:\s*[0-9]+
M1002 set_filament_type:[A-Za-z0-9_-]+
M1002 judge_flag [A-Za-z0-9_]+
M1002 judge_last_extrude_cali_success
M620 S(?:0A|255)
M621 S(?:0A|255)
M624 (?=[A-Za-z0-9+/=]+$)(?:[A-Za-z0-9+/]{4})*(?:[A-Za-z0-9+/]{2}==|[A-Za-z0-9+/]{3}=)?
```

Whitespace between the command token and extension payload is required. The
M1002 colon forms preserve the observed distinction between optional spaces
around the colon and the no-space `set_filament_type:<value>` form. The
M624 payload is validated as a non-empty standard-base64-shaped token, not
arbitrary text.
The M620/M621 values are explicit observed forms, not a general alphanumeric
escape hatch.

Any additional textual command ID or payload variant must first be observed in
the installed supported Orca output and added with a focused rule and test. No
textual remainder is accepted for arbitrary G/M/T commands; in particular,
`G1 garbage` remains invalid.

### Comments and whitespace

Preserve the current line policy: strip the first semicolon and its remainder,
then trim whitespace; blank lines and comment-only lines do not count as
commands. Inline comments after valid code are allowed. A file containing only
comments/metadata/blank lines remains invalid because at least one executable
command line is required.

### Rejected grammar

The validator must continue rejecting at least:

- `G1 garbage`
- `G1 Xabc`
- `random words`
- `G foo`
- `G1 X` under the command-specific bare-flag policy above
- `G28 Z` is not currently admitted by the evidence-backed bare-flag policy;
  it is not asserted here to be permanently malformed
- `G28 Z Pabc T140`
- `G28 Z P0 Tabc`
- `G28 Z P0` unless separately evidenced
- `G28 Z T140` unless separately evidenced
- malformed M1002 forms such as missing payloads, missing required colon,
  nonnumeric action values, or unknown M1002 extension verbs
- malformed decimal command tokens such as `M9833.`, `M9833.2.1`, or `M9833x`

The validator is intentionally only a structural plausibility check. It does
not claim to validate every command's machine semantics, parameter ranges,
ordering, or firmware compatibility.

## Structural validity versus slice facts

PASS. The boundary remains explicit:

```text
supported structural syntax -> parse_gcode() -> required positive layer_count
```

Structurally invalid output maps to `slice_output_invalid`. Structurally
plausible output whose parser facts lack a positive `layer_count` maps to
`slice_facts_invalid`. No slice-stat parsing is moved into the structural
validator and `src/print_engineer/adapters/slicer/gcode.py` remains unchanged.

`execution.py`. It preserves all published Increment 3 guarantees:

- no wildcard or archive substitution;

## 4294967293 diagnostic findings

Reproduced in retained evidence: NO.

The later report gives unsigned Windows-style code `4294967293`, whose signed
32-bit equivalent is `-3` (`4294967293 - 2^32`). The repository retains
successful direct Orca output and successful earlier Phase 3 output, but no
failed-run workspace, exact command capture, executable invocation record,
environment snapshot, stderr/stdout, or pre-existing-file inventory for the
`4294967293` attempt. Consequently exact differences in executable, arguments,
config order/names, model, output directory, archive name, current directory,
environment, timing, repetition, and diagnostics cannot be proven from local
evidence.

Classification for this plan: **D — unresolved independent defect**. It is not
attributed to the validator because the failed process returned nonzero before
the candidate-validation branch, and no evidence connects `-3` to parsing.
It is excluded from this correction. The post-build real smoke must capture
the complete command/input/environment/process diagnostic record; if `-3`
recurs, it must be triaged separately as an invocation/configuration/runtime
issue unless new evidence proves a shared owner. No Orca command/process file
is changed by this plan.
